## Overview
A verification service for source-code escrow. Enterprises licensing critical vendor software already pay an escrow agent $5–15k/yr to hold a deposit. Almost none of those deposits have ever been built by anyone but the vendor. We rebuild every deposit on every release inside a network-isolated runner and issue a signed grade the licensee's vendor-risk team can put in a file. Buyers: the licensee's third-party-risk and BCDR functions at banks, insurers, hospitals, and utilities; sold to vendors as a security-review unblocker.

## Problem
The deposit is a compliance artifact, not an asset. When the vendor is acquired or dies, licensees discover the deposit is missing a private submodule, a license server, a vendored blob, cloud secrets, seed data, or a build toolchain that no longer exists. The escrow industry does sell verification, but as a slow manual annual engagement priced like consulting. Nobody continuously answers the only question that matters: if we opened this today, how long until it runs?

## How it works
1. Vendor adds a GitHub Action that packages a deposit on every release tag: source, a `deposit.yaml` (build command, smoke test, seed data, secrets inventory), and their shipped artifact's hash.
2. Our runner extracts the deposit into a container with egress denied and rebuilds using only what is inside it. Every outbound connection attempt is caught by a recording MITM proxy and denied. **That denied-host log is the product** — it is the exact inventory of hidden dependencies the vendor did not know they had.
3. We grade on a five-item Continuity Rubric: builds offline from clean checkout; artifact matches the shipped release (byte-identical, or functionally equal via the vendor's own test suite); boots and passes a smoke test against seeded data; all third-party deps vendored or mirrored to our proxy; runbook completeness. Score 0–100.
4. Licensee portal shows the current grade, the grade history across releases, the denied-host list, and a "cold start drill" report: wall-clock time from sealed deposit to first successful HTTP 200. Vendor gets the failures privately first, with a fix window before the grade publishes.

## Technical approach
Runners: Docker on Firecracker microVMs, deny-all egress via nftables, plus a `mitmproxy` addon logging every CONNECT. Hermetic builds preferred via Nix flake, with a generic fallback that runs `deposit.yaml`'s build command against a pinned base image plus an offline package mirror (a pull-through cache we populate once at onboarding, then freeze — so "npm install worked" never silently means "the internet worked"). Deposits land in S3 with Object Lock (WORM) and a hash chain, so nobody, including us, can rewrite history. Attestations are signed with cosign and logged to Rekor, so the licensee's auditor verifies our claim without trusting our portal. Control plane: Postgres + a job queue; data model is `vendor → product → deposit(release, digest) → verification_run(rubric_scores, denied_hosts[], artifact_diff)`.

Hard part: build heterogeneity. A generic runner will not survive contact with a 2011 Java monolith. The answer is a paid one-week onboarding per product that produces the `deposit.yaml` — that is the services margin and the moat, because the second year is pure automation.

## v1 scope
- Manual deposit upload (a tarball) — no CI integration yet.
- One runner, Linux x86 builds only.
- Rubric items 1–3 only (offline build, artifact compare, smoke test).
- A single PDF attestation, generated by hand from run output.
- Three design-partner vendors, free.

## Out of scope
The legal escrow agreement and release-condition arbitration — partner with an existing escrow agent, do not become one. Windows/macOS builds. Continuous per-commit verification. Storing the vendor's secrets.

## Risks & unknowns
Incumbents (Iron Mountain, Escrow London) can bolt this on and already own the contracts; the counter is selling licensee-side, where the incumbent is the thing being audited. Vendors may refuse because a public failing grade is embarrassing — hence the private fix window. SaaS licensees increasingly want data export, not source, which shrinks the market. Regulatory tailwind (DORA, ISO 22301 exit plans) is real but slow.

## Done means
Three vendors verified end to end, and one licensee's vendor-risk team accepts our attestation in place of their own questionnaire — plus a live drill where an engineer who has never seen the product boots it from the deposit alone in under four hours.
