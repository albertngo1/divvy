## Overview

A CLI and CI check that answers one question about a compiled Linux binary: *where will this actually run?* It reads the ELF's versioned symbol requirements and dynamic dependencies, compares them against a precomputed matrix of what every mainstream distro release actually ships, and prints a compatibility table — plus a ranked list of which specific symbols are costing you which distros, traced back to source lines. For indie devs, game studios, and anyone shipping a single-binary tool who is tired of "GLIBC_2.38 not found" bug reports from users on Debian stable.

## Problem

You build on Ubuntu 26.04, ship a tarball, and a user on Rocky 9 gets a linker error. The current workflow is: guess, or maintain a zoo of Docker build images, or discover the floor empirically from angry issues. The information needed is fully present in the ELF and in public package metadata — nobody has joined the two into a single answer.

## How it works

1. `toonew ./mybinary` parses `.gnu.version_r` (version needs per shared object) and `DT_NEEDED`, extracting the max required version per library — e.g. `GLIBC_2.38`, `GLIBCXX_3.4.32`, `libssl.so.3`.
2. It joins that against a bundled JSON matrix: for each distro release (Debian 11/12/13, Ubuntu LTSes, RHEL/Rocky 8/9/10, Alpine, Amazon Linux 2023, openSUSE Leap), what glibc/libstdc++/openssl version ships, and the release's EOL date.
3. Output is a table: ✅ runs, ❌ blocked, with the single blocking requirement named.
4. The mischief: **cost attribution**. For each too-new symbol it resolves the referencing relocation back to an object file, then via DWARF to a source file and line, and sorts by "distros unlocked if you avoid this." `arc4random_buf` costing you every RHEL 9 install is a one-line fix; you just never knew.

## Technical approach

Rust, using `object` + `gimli` for ELF/DWARF, `goblin` as a fallback for stripped inputs. The distro matrix is generated by a nightly script hitting the Repology API (`/api/v1/project/glibc`) plus per-distro package indices (Debian `Packages.gz`, Fedora/RHEL `repomd` primary.xml, Alpine `APKINDEX`) and pinned into the release as a ~200KB JSON so the tool is offline and deterministic. Symbol→source attribution walks `.rela.plt`/`.rela.dyn` to find referencing addresses, then DWARF line tables; when unstripped debug info is missing it degrades to naming the object file only. The genuinely hard part is attribution accuracy under LTO and inlining, and handling statically-linked-but-still-dynamic edge cases (`getaddrinfo` pulling NSS at runtime — a static-glibc trap that no symbol table reveals).

## v1 scope

- x86-64 ELF only
- glibc + libstdc++ version floors only (no third-party sonames)
- Hardcoded matrix of 12 distro releases, checked into the repo
- Table output + `--json`; nonzero exit if a `--require debian-12` target fails
- No source attribution — just "symbol X requires GLIBC_2.38"

## Out of scope

ARM/RISC-V, musl cross-analysis, actually fixing the code, suggesting polyfills, a hosted web uploader, macOS/Windows.

## Risks & unknowns

Repology naming inconsistency across distros; vendor backports where RHEL's glibc 2.34 carries patched symbols from later versions (the version table lies); LTO destroying line attribution; whether "symbol floor" alone predicts real failures often enough to be trusted.

## Done means

Running it on a binary built in an Ubuntu 26.04 container correctly predicts failure on Debian 12 and success on Ubuntu 24.04, verified by actually executing the binary in both containers — and the predicted blocking symbol matches the runtime loader's error message verbatim.
